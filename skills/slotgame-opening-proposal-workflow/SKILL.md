# Slotgame 開案企劃流程

## 工作原則

- 預設使用繁體中文與可直接交付的企劃用語。
- 先鎖玩法與流程，再處理機率、美術、程式與正式文件；遵守使用者指定的階段範圍。
- 將每個規則標成「已鎖定」「規劃目標」「待確認」或「待數學驗證」。不得把目標值寫成已驗證結果。
- 將規則寫成可實作規格：說清楚觸發條件、判定時機、事件順序、停止條件、重置範圍、計分公式與例外。
- 將來源腳本、DOCX、PPTX、流程圖、玩家規則與交接文件視為同一交付組。修改規則時同步更新所有依賴項。
- 發現新舊內容衝突時，列出差異與影響，保留待確認狀態；不得自行挑一版假裝已鎖定。

## 判斷任務類型

先檢查工作區與現有檔案，再依請求選擇流程：

- **概念討論**：執行遊戲框架、核心玩法、Symbols、Main Game、Freegame；不要提前做機率或美術。
- **規則修訂**：先定位目前規則來源與版本，再建立影響清單並同步所有依賴產物。
- **完整開案**：完成全部階段與正式交付包。
- **單一交接**：只輸出機率、美術、前端、動畫或玩家規則所需內容，但先驗證其依賴規則已鎖定。
- **文件審查**：先列錯誤、矛盾、缺漏與風險，再給修正方案；不要只做摘要。

完整階段 Gate 與產物清單見 [opening-proposal-stages.md](references/opening-proposal-stages.md)。

## 1. 重建專案脈絡

1. 列出企劃書、簡報、流程圖、規則頁、數學文件、演出規格、生成腳本與測試。
2. 找出目前最高版本、原始生成來源與衍生輸出。
3. 建立或更新三項工作記錄：
   - 規則決策表：規則、狀態、版本、影響模組。
   - 待確認清單：衝突、缺值、未決分支。
   - 交付物地圖：來源檔、輸出檔、驗證方式。
4. 若工作區已有使用者修改，保留並與之整合，不要回復或覆寫未授權內容。

## 2. 鎖定遊戲框架

依序確認：

1. 遊戲名稱、題材與玩家幻想。
2. 新案、換皮或舊案改版。
3. 盤面／輪帶規格與派彩模型。
4. 核心得分條件與連鎖方式。
5. 主要賣點與複雜度上限。
6. 本階段明確不處理的範圍。

若使用者正在選玩法，提供 2–3 個可比較方案，先給建議與理由，再等待選擇。使用者說「鎖起來」「先暫時鎖定」或同義語時，才將該規則改為已鎖定。

## 3. 鎖定核心玩法

按下列順序處理，避免後項反推前項：

1. 派彩模型：Payline、Ways、Cluster、Pay Anywhere 或其他。
2. 盤面與連接：尺寸、方向、斜向是否成立、群組是否合併。
3. 判定順序：初始盤面、得分判定、消除、掉落、補牌、特殊符號生成、再次判定、停止。
4. 一般 Symbols：數量、價值層級、題材功能。
5. Wild：代替範圍、生成位置、生成時機、顆數、倍數算法、是否保留。
6. Scatter：出現位置、觸發數量、派彩、能否補牌出現、是否可被代替。
7. 其他功能：Collect、Hold、Mystery、Jackpot、升級或倍數池。

每個機制至少寫一個正常範例與一個不成立範例。對事件順序使用箭頭流程或逐步表，不要只寫形容詞。

## 4. 定義 Main Game

寫出完整狀態機：

`下注 → 初始盤面 → 得分判定 → 計分 → 消除／變化 → 補牌 → 特殊機制 → 再判定 → 結束`

至少確認：

- 一次 Spin 內多組得分如何計算。
- 多個 Wild 或倍數如何合併。
- 連消／升級何時前進、何時不前進、何時重置。
- 未參與得分的特殊符號如何處理。
- Spin 總分公式與逐步結算範例。

## 5. 定義 Freegame 與 Feature Buy

先完成自然觸發 Freegame，再獨立定義 Feature Buy。不可假設兩者完全相同。

逐項確認：

- 觸發條件、起始局數、進場固定獎與起始狀態。
- 每局與跨局保留的狀態。
- Retrigger／加局是延長同一 Feature 或重開 Feature。
- 加局時局數標示、境界、倍數池、已累積得分的重置／延續規則。
- 倍數何時套用當局、何時進池、何時最終派彩。
- 自然 FG 與 Buy FG 的價格、進場獎、權重、RTP 模型及加局差異。
- 中斷連線、Max Win 與功能提前結束的玩家顯示。

用 `進場 → 初始化 → 每局 → 連消 → 加局 → 最終結算` 順序寫演出流程，並提供一個含加局與倍數池的完整算分案例。

## 6. 建立數學交接

只在玩法鎖定後建立數學內容。明確區分：

- 已鎖定公式與狀態機。
- 規劃目標：RTP、Hit Rate、Feature 頻率、波動、平均回收、Max Win。
- 待數學設定：Paytable、Symbol 權重、倍率權重、上限與保護值。
- 已驗證結果：樣本量、種子、版本、誤差與測試日期。

列出所有計分公式、觸發器、狀態重置點、後端上限與測試案例。後台控管與玩家規則分開書寫。

數學內容需要重新檢視時，逐項鎖定而不是一次確認整包：

1. Bet 單位、派彩公式、加總順序、精度與取整。
2. Paytable 表面值對應的實際 Bet 倍數。
3. 總 RTP、Main Game、自然 Feature 與其他 Feature 的貢獻平衡。
4. Hit Rate 分母、Feature 子局處理及 Trigger／一般得獎的重疊定義。
5. Feature 觸發率、平均派彩、結果區間與零獎保護。
6. Tumble 深度與「倍率到達」／「倍率實際套用」分布。
7. Feature Buy 價格、共用權重、RTP 與回本率。
8. Max Award、超額判定、重抽範圍、次數上限與終止行為。
9. 波動標籤與短、中期玩家資金體感。
10. 樣本量、Seed、信賴區間、逐投注驗證與零誤差對帳。

用公式回算關聯目標：自然 Feature RTP 為「觸發機率 × 平均派彩」，Feature Buy RTP 為「平均實際派彩 ÷ Buy 價格」。若任何公式、Bet 單位、上限或重抽機制改變，舊權重、舊案例與舊模擬立即標記失效。

超額結果若重新 Random，玩家實際看到的是條件化後的最終分布。數學交接必須分別輸出原始與最終 RTP、觸發率、重抽次數、被捨棄 Feature、最後保底路徑及各投注級距差異。玩家 Help 只描述對玩家公開的派彩上限與規則，不放入隱性權重或拒絕抽樣細節。

在宣稱低、中或高波動前，檢查 RTP 集中於 Feature 的比例、Feature 等待機率、無 Feature 區間的直接回收、派彩尾部、短期報酬分位數與最大回撤。高 Hit Rate 不等於低波動。

## 7. 建立題材、Symbols 與演出交接

讓題材服務玩法，不要只換名詞：

- Symbols 表包含代號、名稱、價值層級、畫面位置、功能與辨識重點。
- 特殊符號列出待機、生成、參與、結算、未觸發與退場狀態。
- UI 顯示當前模式、剩餘局數、進度、倍率、池值與本次得分。
- 動畫順序必須符合後端事件順序，且讓玩家分辨「出現」「參與」「收集」「派彩」。
- 玩家規則只寫玩家可理解與驗證的規則；後端腳本、封包限制、強制控表放在工程備註。

## 8. 產出與同步交付物

依需求建立：

- 開案企劃書 DOCX。
- 開案簡報 PPTX。
- 可編輯 Draw.io 流程圖與 Axure 可用的 SVG／PNG。
- 玩家規則頁與繁中／簡中／英文文案。
- 機率、美術、UI／前端、動畫、QA 交接文件。
- 可重建產物的生成腳本。

建立或修改 DOCX 時使用文件技能；PPTX 使用簡報技能；完成後做結構與視覺 QA。不要只修改生成輸出而漏掉來源腳本。

## 9. 執行一致性驗證

在宣告完成前，依 [consistency-checklist.md](references/consistency-checklist.md) 檢查：

1. 名稱、版本與 Symbols 是否一致。
2. Main Game、Freegame、Buy FG 的觸發與重置規則是否一致。
3. 公式、逐步案例與表格是否算得回去。
4. 玩家規則是否排除內控資訊。
5. DOCX、PPTX、Draw.io、Axure、UI 文件與生成腳本是否同步。
6. 所有未決衝突是否仍明確標為待確認。

## 交付回報

完成時只回報高訊號內容：

- 已鎖定或修改的核心規則。
- 產出的可點擊檔案。
- 已執行的驗證。
- 尚未完成、未驗證或需要使用者決定的項目。

處理特定遊戲時，只讀取該專案提供的規格與決策紀錄；不得把其他遊戲的機制或數值默認套用。
